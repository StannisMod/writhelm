# H1 — governed agent workflow inside OpenCode

Contract K-HARNESS, revision 5. Status: H1 boundary, practical-control, connected-work coordination, deterministic correction and grouped delivery amendments approved,
including initial cooperative execution. Component implementation/qualification still required. First user-pilot
target, not a claim of implemented orchestration or acceptance of the whole draft specification.

## H1-01 — Canonical control and native execution

Writhelm owns canonical work state and allowed transitions; an OpenCode V2 plugin controls native
sessions, work areas, context and user interaction. Do not replace OpenCode's model runtime or call
an MCP tool catalogue a governed harness. Canonical records remain in one private instance Git root;
native conversation history remains in OpenCode, not a second normative corpus.

Technical identity/authority/resource checks and semantic obligations are distinct. Service enforces
typed transitions, permissions, exact bindings and explicit gates; planner/reviewer judge natural-
language scope, sufficiency and meaning. A prose criterion is not proved by a service field/model
report. Do not replace semantic review with a predicted file allowlist.

Canonical Git records significant task/assignment/authority transitions, checkpoints, results,
reviews/decisions and integration facts. Heartbeats, UI and streaming/tool observations may remain
operational/derived/native or retained artifacts; do not commit every event by default. If one supports
a consequential decision, retain its applicable basis with that decision. No operational cache may
hold unique canonical authority or replace recoverable required state.

## H1-02 — Owner and planner

Owner states the objective in the primary conversation. Planner reads exact applicable knowledge,
identifies necessary decisions and obtains structured in-harness approval for new product/design
meaning. Routine technical actions do not require constant owner confirmations. Owner keys remain
outside the model; U1/T1 and current service grants remain binding.

## H1-03 — Canonical tasks and dispatch readiness

Planner creates separately versioned tasks with exact inputs, read/write/decision scope, constraints,
dependencies/readiness, acceptance/escalation/output and execution/verification profiles. Workers
receive those contracts, not parent transcript summaries. Immediately before assignment service
binds exact task/snapshot/complete mandatory packet and checks rights, dependencies, known conflicts,
withdrawals and claims. Older valid snapshots remain possible; no latest fallback or omitted inputs.

## H1-04 — Native assignments and external-effect uncertainty

Plugin creates/binds distinct native sessions/work areas, applies each effective model/effort/budget
profile and starts only with valid service assignment. Workers have scoped identities, no owner/store
access. Unknown native create/start outcome requires reconciliation before retry, not a duplicate
worker. Git publication and external OpenCode/model effects are not one atomic transaction; no
exactly-once model execution promise is inferred.

## H1-05 — Context, execution boundaries and continuity

Control complete mandatory inputs and every applicable outgoing model request at a qualified boundary,
not merely by task instructions. Pause/stop/rebind/resume and tool safe boundaries are explicit.
Substantial progress/remaining obligations are checkpointed; after compaction/restart restore exact
task/profile/snapshot/assignment from service and reconcile actual artifacts. Summary is not authority.
Ordinary updates notify without silent rebind; withdrawal blocks affected use at supported boundaries.
Initial H1 uses explicit cooperative E-COOP-1: separate worktrees, qualified native permissions and
whole-diff review, NOT an OS guarantee against arbitrary shell escape. Reviewer gets a read-only exact
snapshot and separate report/scratch. Service authorization, owner-key exclusion from worker inputs
and canonical-store access separation remain mandatory. Strong shell/subprocess/OS containment is
a separately qualified profile, not a first-pilot prerequisite. This is an explicit owner amendment,
not a silent waiver derived from T1, which originally scoped the approval channel only.

Native-first clarification accepted on 2026-11-05: the required guarantees do not prescribe duplicate
runtime machinery. Start with OpenCode's native lifecycle/permissions/compaction, configure relevant
reserves and qualify actual behavior for the chosen profile. If sufficient, reuse it directly.
Additional guards require an evidenced gap; do not presume a custom per-LLM-call interceptor,
counter/summarizer or service round trip. Compaction trigger alone is not proof of a hard ceiling;
any change to the required guarantee needs explicit agreement in the context/profile contract.

Task-shaped continuity clarification accepted on 2026-11-05: information needed to continue or
justify results must not exist only in conversational context. Restore exact task/norm/input records
separately from targeted extraction of residual working knowledge, with sources/status/uncertainty;
do not replace obligations by a narrative summary. Relevance is to remaining obligations, including
constraints/discoveries from already completed steps. A worker may retire active context after durable
complete handoff without waiting for downstream result acceptance; outstanding effects/obligations
must remain explicitly recoverable. Planner continuity includes the frontier of active tasks,
dependencies and awaited decisions/events. Persist/confirm continuation state before discarding old
active context; this is not a cross-system atomicity promise or a requirement to delete audit artifacts.
Implementation details and the proposed K-CONTEXT contract as a whole remain subject to their own scope.

The owner clarified that SOPs address recurring consequential behavioral failure patterns, not an
exhaustive whitelist of permitted reasoning/actions. Missing SOP coverage alone does not forbid
ordinary authorized work; task scope, service authority and existing general constraints still apply.
Retrospective observations/proposals do not automatically become prescribed rules: interpretation/
normative disposition stays with the owner. Exact SOP admission/generalization/lifecycle procedure
is under discussion, not ratified by these continuity clarifications.

## H1-06 — Evidence and independent verification

Worker results identify exact artifacts/tree/changes/checks. Reported success is not verification.
Fresh-context non-author reviewer assesses an immutable result with separate writable report/scratch;
reviewer cannot edit assessed code/tests. Findings require concrete requirement-linked scenarios.
Remediation is a separate task and new exact result, not a review-side fix or producer self-approval.

The primary may propose an exact corrective patch as an attributed artifact when the correction is
already determined. Applying it is a separately authorized deterministic operation, not another LLM
assignment or a grant of unrestricted editing to the primary. The primary is an author of those
changes even if a mechanical adapter writes the files. No patch author, original producer or merely
renamed role/session may independently verify the resulting changes. See TASK-08, EX-08 and EV-09.

Default delivery is bounded execution, planner control of bearing requirements/interfaces/invariants,
any already-determined planner corrections applied mechanically, targeted checks and a local
commit-candidate. Planner control is not independent review, and a commit is not verification,
acceptance or integration. Do not create another LLM applicator or a new reviewer per small patch.
Plan a coherent bounded MR/umbrella result set and its independent non-author whole-diff review
before execution; that gate precedes acceptance/integration of the set. Existing prescribed earlier
gates remain binding. Exact subjects, applicable evidence and author exclusion are not replaced by
a group label. See EV-10 and TASK-09.

## H1-07 — Routine acceptance and integration

Planner may accept routine conforming results within approved task/design scope under D12, after
checking consequential review claims and applicable evidence. No waived blockers/design changes.
Integrate only the applicable accepted result; integration changes need appropriate verification.
Proposed, implemented, verified, accepted and integrated remain distinct linked facts, not one DONE.

## H1-08 — In-harness control and pilot boundary

Human sees tasks/dependencies, workers/progress, blockers/findings, pending decisions and pause/resume
inside OpenCode. First complete pilot: a real code change with two workers, dependency handling,
pause/resume, review, remediation and integration from the primary OpenCode flow. No manual context
copying or external approval app. Unknown/unsupported request accounting or execution restrictions
do not qualify as enforced merely because the prompt asks for them.

Linux, Windows and macOS remain targets with separately qualified adapters; OpenCode is first, not
all harnesses/models/providers. M1 is an unaccepted foundation, not a separate user pilot. Cheap
component checks continue; native/combined/expensive qualification uses an agreed combined plan.
Prior findings/held gates remain visible, not accepted by changing pilot scope. Live inference/paid
pilot and spend limits require separate owner authorization before execution.
