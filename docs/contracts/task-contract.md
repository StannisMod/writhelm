# Canonical tasks, exact results and authorized acceptance

Contract K-TASK, revision 3. Status: original decisions, practical-control and connected-work coordination amendments approved, including explicit
state-changing planner acceptance of an exact result. No task API implementation/pilot is claimed.
Governing scope: [K-HARNESS revision 3](agent-workflow.md), accepted D9/D10/D11/D12/D15 and
WH-09/10/17/19. Existing snapshot/withdrawal/authority laws remain binding.

## TASK-01 — Stable identity, immutable revisions

Task has stable project/task identity and immutable revisions. Each revision identifies objective,
exact inputs/knowledge refs, read/write/decision scope, constraints, dependencies/required readiness,
acceptance, escalation, expected output and execution/verification profiles. Contract changes create revisions;
title/current pointer is not executable identity. Canonical tasks share the private instance Git
root with authority/workflow/results, not native chat history.

## TASK-02 — Routine planner authority

Authorized planner prepares routine tasks within approved product/design/decision scope. Owner does
not approve every delegation. Implementation cannot bypass required design approval; research/design
may examine proposals without promoting them to obligations. Worker cannot widen its active scope,
retarget inputs, self-verify/accept or grant review exceptions. Exact task-operation/assignment grants
must be specified before API exposure; existing knowledge PLAN is not silently expanded into
unrestricted dispatch/accept/integrate authority.

The immutable contract is not the mutable work plan/progress tracker. Worker may refine sequence,
inspect additional files in the pinned base, form/reject hypotheses and add appropriate checks
within scope without task revision/rebind. Scope is semantic, not an exhaustive predicted file list;
another affected file is not by itself a contract change. Changed objective, requirements/base,
acceptance or authority still requires applicable explicit revision/decision.

## TASK-03 — Draft versus executable contract

Draft may have explicit unresolved inputs/dependencies but no launch authority. Immediately before
assignment bind complete exact executable revision, chosen compatible valid snapshot and mandatory
packet/inclusion manifest/profile. Recheck rights, readiness, known conflicts/withdrawals and claims.
Missing, denied, ambiguous, conflicting or oversized required inputs refuse/escalate, not omit or
truncate. Older valid branch snapshots are allowed; no latest/title fallback or unvalidated draft-era
binding. Mandatory applicability/closure mechanics have their own contract, not an LLM proof.

Exact input base differs from its loaded view: additional reads from the same pinned code/knowledge
base don't substitute a new base or automatically require rebind. Service checks closure of declared
mandatory inputs; discovery of all semantically applicable norms remains planner/reviewer work.
New relevant conflict/gap is explicit and may block affected work under existing laws, not proof
that every previously unknown source was mechanically certified at dispatch.

## TASK-04 — Dependencies specify consumer readiness

Dependency states producer and readiness needed by consumer, not a generic DONE. Drafts may reference
not-yet-produced work; executable inputs pin exact selected results and outstanding coverage. Using
implemented/cheap-checked work is allowed only by explicit plan, never certifies deferred review.
Integration gate still requires prescribed checks. Cycles/unmet requirements block affected work,
not independent work. Delegations/splits have separate versioned tasks; claims/native assignment
mechanisms are specified in K-DISPATCH rather than inferred from a task status.

A dependency may express a condition needed to continue a part of one connected functionality,
not merely delivery of another task's artifact. Identify the responsible work, the condition and
required confirmation. Satisfying the agreed condition does not require the planner to restate or
reassign already authorized work. The engine carries confirmed resolution through to eligible
continuation under K-DISPATCH; generic DONE or an unverified producer claim is insufficient.

## TASK-05 — Do not rewrite active assignments

Assignment keeps original task revision/inputs/profile. Changed terms require new revision and
explicit stop/rebind/resume through supported boundaries. Old progress/evidence/results remain bound
to original inputs. New draft/revision does not automatically replace running work. Ordinary updates
notify without forced rebind/stop; withdrawal blocks affected use at qualified boundaries. UI state
alone cannot prove in-flight execution stopped.

Fulfilling an existing behavioral/interface agreement differs from changing it. Changes to behavior,
interfaces, responsibility or authority require the applicable decision; they cannot be hidden by a
"fixed, continue" notification. Exact bases/results remain bound: environment preparation or an
applicable explicit rebind must not silently substitute an assigned base.

## TASK-06 — Attributed progress and exact results

Checkpoint binds task revision/assignment, reported work, artifacts/changes/evidence, remaining
obligations and blockers. Report is not proof. Result binds same task/assignment, producer, exact
changes and assessed repository/tree or explicit dirty-content digest as applicable. HEAD alone is
insufficient for dirty work. Missing exact result/evidence identity cannot advance verification.
Checkpoints support restart, not transcript/summary substitution for task authority.

## TASK-07 — State-changing acceptance, separate integration

Preparation, execution, produced result, verification, acceptance and integration are distinct linked
facts with explicit authorized transitions, not merely comments or one global DONE.

Worker submits result R1; fresh-context non-author reviewer records assessment of exact R1 without
editing assessed code/tests. Planner checks task criteria, applicable evidence and findings, then
issues **accept result R1**. Service verifies current rights/conditions, refuses unresolved blockers
or missing required checks, and records exact result, accepting actor and basis: R1 becomes
**accepted**, eligible for its authorized integration. Planner DOES change state through the service,
but cannot fabricate verification or accept through blockers.

Service verifies typed rights/bindings/required check records and explicit blockers; it does not
automatically prove natural-language criteria or factual truth. Planner/reviewer remain accountable
for the corresponding semantic judgment and consequential evidence checks.

Independent review of implementation remains required under its verification plan and may cover a
related result/change set rather than a full cycle per tiny task. Planner checks reviewer reports;
their mere existence does not recursively require another reviewer indefinitely. This is not a
planner/worker permission to waive a mandatory independent gate. Required scope/grouping/readiness
is planned explicitly, not invented after a failed check.

Integration is a separate fact on an exact target/resulting tree. Acceptance does not mean a merge
already happened; changed integrated bytes need appropriate verification. D12 permits routine
conforming acceptance/integration; owner still decides design changes/exceptions/agreed checkpoints.
Remediation is a separate task/new result, not reviewer code editing or R2 inheriting R1 checks.

## Derived obligations and readiness

Refuse incomplete executable contracts, unapproved implementation scope, denied/withdrawn/conflicting
inputs, dependency cycles/unmet readiness, revision overwrite and wrong task/assignment result reports.
Permit older valid snapshots and explicitly planned implemented-result dependencies without false
verification. Preserve historical bindings after revisions. Authorized exact-result acceptance must
succeed with applicable criteria/checks; worker self-acceptance and blocker bypass must refuse.
Exact schemas, new capability semantics/namespaces/journal compatibility and native lifecycle are
separate design/readiness inputs; approval does not silently extend existing formats or authorize
native/model execution, blanket implementation or source publication.
